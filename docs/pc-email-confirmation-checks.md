## Reproduced findings

1. **An old session can make a failing confirmation link show success.** Start the actual confirmation effect with a synthetic token_hash and verification pending. Deliver INITIAL_SESSION for an existing synthetic owner. The UI becomes success before verification resolves; when the verification then returns error/null session, success persists, including after the timeout. This reproduces in both languages. The onAuthStateChange handler accepts any non-null session, while finish locks the first result and ignores the eventual verification failure. As a control, an invalid link without a session event renders the expected error. The no-link path also reports success from getSession without verifying a link. This establishes misleading confirmation status and missing linkage to the current operation, not an authentication bypass, server-side email confirmation, account takeover or disclosure of credentials.

2. **Thrown verification failures escape as unhandled promise rejections.** Make actual verifyOtp reject with a synthetic local error. The component invokes confirmSession without a rejection handler; a bounded diagnostic listener observes the synthetic rejection. The UI stays checking until its ten-second timer renders a generic invalid/expired-link error. The diagnostic triggers the timer directly rather than waiting or making a network request. Real network/storage/provider exceptions and every transport mode have not been live-tested.

## Pending / proposed repair

Require evidence from the current confirmation operation before reporting link success; an existing or changed session must not independently complete a pending invalid request. Preserve ordinary supported signup confirmation modes and safe internal return behavior, bind any accepted result to its verified user, and account for SDK automatic URL processing/effect replay before choosing a code-exchange design. Do not infer that every confirmation link can safely be exchanged twice or that an already-consumed code must be retried.

Handle returned and thrown verification/session errors explicitly with safe bilingual copy and bounded waiting; avoid leaking URL token/error details. Add actual-source regressions for valid/invalid links, old-session events, changed-owner events, rejection, timeout, effect replay and unmount. Obtain repair authorization before changing app source, recovery-only testing permission before any real token/account/mail or deployment activity, and distinct formal release approval afterwards. No fix or external write has been performed by this diagnostic.

## Authorized repair — local verification only

The user requested repair. The confirmation page now captures/validates this request's token hash, PKCE code or implicit token pair exactly once and removes link material from history before explicit SDK consumption. Missing, error, duplicated, mixed or recovery/invite-shaped inputs cannot be promoted to signup success by an old session. Returned/thrown errors have generic bilingual handling and bounded waiting; effect replay shares one task, real unmount/timeout cancels its eligibility, and the enter button rechecks the verified identity with a synchronous duplicate-navigation guard. Page title follows language. Historical diagnosis is explicitly pinned to formal 1d1c3cc; it is not a regression expectation against repaired source.

A dedicated tab-scoped confirmation SDK client (no URL autodetection, no auto refresh, no memory/persistent fallback) holds verification results until the server confirms their user id and email confirmation timestamp. Only then may the main client receive the session. Main-client automatic URL consumption is disabled only when initialized on /auth-confirmed, preventing a second exchange/implicit consumption while preserving reset-password and Google route behavior. Code mode copies only the exact main verifier to the confirmation client's key and conditionally removes that original value, preserving a newer verifier. Cleanup touches only this feature's temporary keys, never drafts, main auth or browser-wide data. Already-pending SDK requests cannot overlap a new same-document confirmation attempt.

Main-session writes have an operation-scoped guarded-storage predicate: even if the SDK is awaiting its user recheck, a cancellation or changed current owner prevents the old verified user/token (including refreshed tokens for that user) from being persisted. Different-owner/unrelated writes are not denied. Policy rejection does not falsely mark browser storage blocked; normal storage failure latching remains unchanged. The guard is released after the SDK operation settles. Session events are used only to invalidate a request, never as proof of confirmation success, and handlers remain synchronous without SDK calls.

Local actual-source regressions cover parsing, all three valid formats, old INITIAL_SESSION while verification fails, returned/thrown session/verification/server-user/save failures, wrong/unconfirmed users, owner changes with/without events and A→B→A, cancellation, timeout, unmount, cleanup failure, missing verifier, newer-verifier preservation, late guarded write rejection, pending-attempt exclusion, bilingual UI, URL stripping failure, effect replay and duplicate/stale enter clicks. An installed-SDK suite runs hash/PKCE/implicit flows in synthetic window/storage with all fetches mocked: SDK initialization does not consume the URL, each one-use verification/exchange occurs once, confirmed identity transfers to the main tab key, and temporary/verifier cleanup retains unrelated text. No real browser/network/link/account/mail/backend mutation was involved.

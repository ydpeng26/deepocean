## Findings

1. **Two return-path validators allow a browser-normalized external destination.** Auth and auth-confirmed accept strings beginning with `/` except literal `//`. The actual validators accept a leading slash followed by backslash; URL-standard parsing resolves the representative synthetic path to a different origin. Both components subsequently assign accepted `next` directly to `window.location.href`. No external destination was visited. Ordinary absolute and literal double-slash URLs are rejected; ordinary `/offline-sync` is retained. Scope: a crafted return URL can potentially send someone to an external site after the relevant successful flow; this does not demonstrate transmission of passwords, sessions or tokens. OAuth/confirmation URL concatenation has other behavior and was not live-tested. Recommended repair: one shared same-origin internal-path policy that accounts for browser URL normalization, backslashes/control characters and safe fallback, with actual consumer tests.

2. **Reset readiness is not bound to the verified account/session through submit.** The actual reset component verifies a synthetic recovery token yielding account A and unlocks the form. In the local model, the current session then changes to B while that same component stays mounted; submit invokes `updateUser` against current B, with no owner recheck or auth-change cancellation. No real password was changed. This requires a same-tab session change while the reset page remains mounted; merely signing in independently in another sessionStorage-isolated tab is not established to cause it. Ordinary navigation to the login page may unmount the component, so UI reachability and session propagation still require recovery investigation. Recommended repair: bind readiness to verified user/session, invalidate on owner/sign-out changes, revalidate before mutation, ignore stale async verification/results on unmount/change and retain failure guidance. A mutation already sent cannot be assumed undone.

## Controls verified locally

- The actual authenticated route guard redirects to auth on absent session or session-read error and accepts a present session. This is an initial guard model, not live server-token verification, expired-session refresh, back-forward cache clearing, cross-tab logout, or RLS acceptance.

No application source was modified to satisfy these checks.

## Authorized repair — local only

The user explicitly requested repair. `safeAuthReturn` is shared by auth and confirmation validators and re-applied at their actual navigation/confirmation/OAuth-return consumers. It rejects non-root-relative, control/space/backslash and browser-normalized foreign-origin or double-slash-path destinations; valid paths are returned as canonical path/query/fragment. Invalid input falls back to the existing `/dives` destination. It does not follow URLs, replace existing origin configuration, expand OAuth allowlists or alter provider credentials.

The reset page now binds readiness to the session user and access token returned by token verification, checks the current session and server-verified bound user before readiness and submit, synchronously latches account/sign-out changes, clears sensitive input and locks the form on mismatch. Observed A→B→A changes remain invalid. Verification is shared across development effect replay, with per-effect active guards and subscription cleanup. Stale async verification/submission completion cannot update an unmounted/new-owner UI. Inputs are disabled while submitting; normal same-owner events do not cancel. Current-session rechecking after the update also avoids ordinary stale success/logout of a different account. Expected own sign-out does not turn a completed normal flow into an invalid-link screen.

Most importantly, the password mutation transport carries the **verified token explicitly**, rather than re-reading whatever account the shared SDK contains when its request runs. The current installed SDK source (`node_modules/@supabase/auth-js/src/GoTrueClient.ts`, `_updateUser`) confirms the existing API is `PUT /auth/v1/user` with access-token bearer auth. The new transport uses the same endpoint/body, public configured API key, an explicit two-project backend allowlist, a 30-second timeout, no cookie credentials and no-store. Response status/user id and current-operation predicate are checked before declaring completion. No token, password or response payload is logged. A request already dispatched may still change verified A even if the UI later changes; cancellation does not undo server mutations or promise aborting an in-flight request. Original-token expiry fails closed and requires a fresh link rather than silently authorizing another session. This is not a claim of an atomic transaction spanning all external auth-client session changes and sign-out internals.

`scripts/pc-auth-boundary-regression.mjs` executes actual current modules/components in local no-network models. It passed both validators against external/normalized/control/backslash cases, preserved ordinary query/fragment/Unicode paths, locked absent/expired/server-rejected verification, normal verified-A update/logout, same-owner events, effect replay without re-verification, changed-owner with/without auth events, sign-out and A→B→A invalidation, owner changes while verification/server-check/update is pending, stale-handler rejection, disabled pending inputs, no late unmount state writes, and no wrong-account success/logout in the modeled interleavings. The actual transport was separately exercised with a stub fetch: its header remains A's explicit verified token independent of the shared session; cancelled calls, failed HTTP response and mismatched returned user are rejected.

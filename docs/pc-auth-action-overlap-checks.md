# Auth action overlap diagnosis — 2026-10-25

The user requested continued checking after formal release 6d4a602b3cb04852cb5194f74a3ee9a1d1e90c7e. Application source remains identical to that release. This diagnosis does not authorize repair, deployment, real sign-in, mail, account fixtures or user-data mutation. Existing screenlog.0 is not changed.

scripts/pc-auth-action-overlap-diagnosis.mjs executes the actual auth component in a deterministic hook model for zh-CN and en. It fills only synthetic input and holds each modeled SDK call pending. After a re-render (not stale/same-tick event replay), it verifies:

- A reset-mail request disables its own button but leaves the password sign-in submit enabled. Submitting starts the modeled password sign-in before reset completes.
- A password sign-in disables its submit button but leaves Forgot password enabled. Clicking it starts a modeled reset-mail request before sign-in completes.
- A pending Google entry likewise leaves Forgot password enabled; clicking it starts a modeled reset-mail request.
- As a control, repeated password-form submission is synchronously blocked by submittingRef and starts only one sign-in.

The installed Supabase SDK is also tested directly with a synthetic .supabase.co origin and all fetches mocked. Both POST token/password and POST recover reach the mock before either is released, confirming no SDK-level mutual exclusion between those operations. The login response is a synthetic rejection; no session or password is established. No request reaches any server and no mail is sent. Google authorization is modeled at the entry only, not performed.

Cause: loading/submittingRef, resetBusy and resendLoading are separate partial guards. handleSubmit checks only submittingRef; requestReset checks only resetBusy and feature availability. The form submit's disabled condition uses loading alone, while Forgot password uses resetBusy alone. handleGoogle itself considers other busy states, but requestReset does not respect its submittingRef. This is a UI/request-coordination issue that permits conflicting simultaneous actions and potentially extra mail requests, not evidence of account takeover, wrong-account password mutation or bypass of server-side mail rate limits. The newly released reset-link verification isolation remains unchanged.

Suggested repair, not implemented: unify synchronous action ownership across password login/signup, Google entry, resend and reset request, align visible disabled states with handler guards, and release only the owning operation on returned/thrown failures. Preserve bilingual feedback and retry without making real mail/authorization requests. Recovery-only deployed-page acceptance would require separate permission after local repair. Real-mail recovery, formal Google user-assisted login and temporary recovery Google configuration cleanup remain separate open follow-ups.

## User-authorized local repair

The user requested implementation. The auth route now has one synchronous operation ref with a unique object ticket for password sign-in/signup, Google entry, confirmation resend and password-reset request. Every handler must acquire that ticket before validation, storage-backed work, feedback or SDK/provider calls; blocked competing/stale handlers return before reprobing storage. Only the exact owning ticket can release it. Returned and thrown errors and validation exits release in finally; a reported Google redirect retains ownership while navigation is pending, preserving the previous redirect semantics. One derived action state drives loading labels and every account button/tab/input disabled state plus aria-busy on the form, preserving credentials and existing bilingual feedback, redirects, storage and safe-return behavior.

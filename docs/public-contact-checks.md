## Implementation and privacy

- `/contact` is a standalone public bilingual page, with home/language controls. Homepage header and login header link there outside auth-disabled controls. It never requests or requires an Auth session or sends a user token. Contact remains usable if auth-session storage is denied. The member navigation retains the existing authenticated contact form.
- Fields: category, 1–3000-character message, optional syntactically valid email up to 254 characters; no password/code/photo attachments. Administrator-only visibility, optional-email purpose, no guaranteed reply, basic limit identifiers and loss of unsent drafts on refresh are explained. Email is not an account lookup and triggers no email or automatic reply. Administrators review public.guest_contact_messages through the protected dashboard; no admin UI or notifications are claimed.
- Synchronous submission lock, stable request UUID/visitor key, pending disable, safe errors, retained failed message/email, exact receipt confirmation, and no post-unmount UI changes. Browser identifier is stored locally when possible; denied storage falls back to page memory. Neither message nor email is persisted in local storage.
- New `guest-contact` Edge Function is deliberately public (`verify_jwt=false`) to handle login failures. It is recovery-origin/project bound, accepts POST and preflight only, limits body bytes/read time, accepts exactly six allowed fields, rejects the honeypot, and forwards only one fixed RPC. It does not trust supplied user IDs, table names, timestamps or Authorization headers. HMAC domain separation derives browser, network and exact-payload hashes using the existing server-only project secret; raw network/browser identifiers are not stored in the inbox. No new secret is exported to the browser, local files or logs. Request body/email are not logged by our code; platform infrastructure logs remain subject to provider behavior.
- New table is RLS-enabled with no browser-role policies or table grants; anonymous and authenticated roles also cannot execute the submission RPC. The RPC is SECURITY INVOKER and service_role-only, with a role check and empty search path. It returns only a receipt UUID, never rows/email/body. Identical signed-payload retries confirm the existing request, while changed-content reuse conflicts. Receipt IDs are not read capabilities.
- The database serializes submission checks with one short transaction advisory lock and indexed rolling-window queries: browser 1/minute and 5/24h, network 3/minute and 20/24h, global 30/minute and 300/24h. The Edge server supplies server-derived hashes and DB time. Global caps cannot be bypassed by rotating browser IDs/network headers. Network headers may be shared/missing/spoofed, so they are supplementary and not asserted as verified identity. These are basic anti-spam/storage caps, NOT a CAPTCHA, proof of a human or comprehensive DDoS prevention; a quota can be exhausted and legitimate visitors may need to retry later. No existing rows are automatically deleted.
